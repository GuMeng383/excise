# 从「控制台小游戏」到「AI Agent 平台工程师」——12 个月成长路线

> 目标岗位：字节跳动 后端 / AI Agent 应用研发（校招或社招早期）
> 配套项目：本项目（多人推理社交平台 Excise）从单机控制台一路演进成「人类 + AI Agent 混战」的在线平台
> 适用前提：每周可投入 **15～20 小时**（周末 8h + 工作日每天 1.5h）。如果你每周能到 25h，整体可压缩到 9 个月。
> 文档约定：`P0`＝第 0 阶段，`Gate`＝通过标准（不达标不进下一阶段）。

> ⚠️ **本文是"通用长期路线"。你的实际执行以 [`6周冲刺-1月跑起来.md`](6周冲刺-1月跑起来.md) 为准**——
> 因为你是大二在校生、目标是 2027 年 1 月项目可运行，P0～P2 的时间被压缩并重排了。
> 本文的 P3 及之后的阶段、以及第六节「AI Agent 专项」仍然完全适用。

## 三、三条总原则

1. **一个项目，反复重写，而不是做十个玩具。**
   同一个"推理社交平台"，用四种形态各实现一遍（控制台 → Socket 并发 → Web 服务 → Agent 平台）。
   每重写一次，你都会发现上一次设计的问题——这就是"系统设计经验"的唯一来源。

2. **每学一个知识点，必须落到项目里，并写一篇能给别人讲清楚的笔记。**
   只学不落地 = 面试时说不出来；只做不总结 = 三个月后忘光。

3. **算法是"每天一点"，不是"突击一个月"。**
   每天 1 题 + 周末 2 题，坚持 40 周 ≈ 350 题，足够覆盖字节的手撕范围。

## 五、阶段详解

### P0（第 1～2 周）：先让项目"像个工程"

**为什么先做这个**：一个没有 git 历史、业务类里打印日志的项目，面试官看一眼就会觉得"这是练习代码"。这一步成本极低、收益极高。

**学什么**

- Git：`init / add / commit / branch / merge / rebase / tag`、commit message 规范（Conventional Commits）
- Maven：依赖作用域、多模块、`mvnw`、生命周期、插件
- 日志：SLF4J + Logback，级别、占位符、避免 `System.out`
- 分层：Controller / Service / Domain / Repository / View 的职责与依赖方向
- 测试：参数化测试 `@ParameterizedTest`、`assertAll`、`@DisplayName`、JaCoCo 覆盖率
- 异常设计：受检 vs 非受检、自定义异常、不用异常做流程控制

**项目产出（V1）**

1. `git init` + 首次提交，`.gitignore` 补上 `target/`、`.idea/`
2. 修掉代码评审里列的 7 个 Bug（EOF 崩溃/死循环、消息矛盾、`allPlayersReady`、NPE、静默失败、丢弃发言、死代码）
3. 拆出 `ConsoleView`：`Player` / `Room` / `VotingService` 不再出现 `System.out` 和 `Scanner`
4. `votes` 收进 `Room` 字段，删掉与 `initVotes` 重复的 `resetVotes`
5. 用 SLF4J 替换所有日志输出，`logback.xml` 配两个 appender
6. 测试补齐：投票平票、淘汰、四种胜负判定、`equals/hashCode`
7. 接入 JaCoCo，核心包覆盖率 > 70%

**Gate（不达标不许进 P1）**

- [ ] `mvnw verify` 一条命令跑通全部测试 + 覆盖率报告
- [ ] 业务包里 `grep -r "System.out" src/main/java` 结果为空
- [ ] GitHub 上有仓库，提交历史 ≥ 10 条，message 规范
- [ ] 能白板画出 V1 的分层图，并解释"为什么 View 依赖 Domain，反过来不行"

**面试可讲点**：*"我重构过一个自己写的项目，把 UI 从业务逻辑里剥出来，覆盖率从 0 提到 70%，并发现原有两个校验规则已经不一致了——这让我理解重复代码的代价。"*

### P1（第 3～6 周）：Java 深入 + 并发 + 网络

**为什么**：这是"后端工程师"的分水岭。不会并发和多线程，后面 Spring、连接池、Redis 全是黑盒。

**学什么**

| 主题 | 必须掌握到"能讲清原理"的程度 |
|---|---|
| 集合源码 | `ArrayList` 扩容、`HashMap` 哈希扰动/树化/并发问题、`ConcurrentHashMap` 分段/CAS |
| 泛型 | 类型擦除、通配符 PECS、桥方法 |
| JVM 基础 | 内存区域、对象头、GC 算法与分代、常见 OOM 排查、`jstack/jmap` 会看 |
| 并发 | `synchronized` 与锁升级、`volatile` 与内存屏障、`AQS`、`ReentrantLock`、`Condition` |
| 并发工具 | 线程池七参数与拒绝策略、`CompletableFuture`、`BlockingQueue`、`CountDownLatch` |
| 网络 | TCP 三次握手/四次挥手、粘包与拆包、`Socket`/`ServerSocket`、NIO `Selector`、HTTP 报文格式 |

**项目产出（V2：Socket 多人联机版）**

1. 服务端用 `ServerSocket` + 线程池处理多个客户端，客户端用控制台连接
2. 自定义应用层协议：`长度(4B) + JSON body`，解决粘包/拆包
3. 房间管理：`ConcurrentHashMap<Integer, Room>`，每个 Room 一把锁或一个单线程 Executor
4. 把游戏状态机做成严格的状态迁移（`WAITING → PLAYING → FINISHED`），非法迁移抛异常
5. 断线重连、心跳、超时踢人
6. 压测：本地 200 个客户端同时连接，观察线程数与内存，写一份压测报告

**Gate**

- [ ] 手写一个线程池（`submit / 任务队列 / 拒绝策略 / 关闭`），能讲清和 `ThreadPoolExecutor` 的差距
- [ ] 手写一个 LRU（`LinkedHashMap` 版 + 双向链表 + `HashMap` 版各一）
- [ ] 能解释"为什么 `HashMap` 线程不安全"，并能构造出并发扩容出问题的场景
- [ ] 压测报告能给出 QPS、平均延迟、线程数曲线
- [ ] 200 客户端联机跑完整一局不崩

**面试可讲点**：*"我把单机版改成了 Socket 联机版，自己设计了带长度前缀的私有协议解决粘包，房间状态用单线程 Executor 串行化来避免锁竞争，200 并发下 P99 延迟 X ms。"*

### P2（第 7～12 周）：Spring Boot 全栈后端

**为什么**：字节后端岗位的工程基线就是 Spring 生态 + MySQL + Redis。这一阶段的目标是"能独立交付一个真实服务"。

**学什么**

| 主题 | 内容 |
|---|---|
| Spring 核心 | IoC/DI 原理、Bean 生命周期、AOP 与代理、循环依赖与三级缓存 |
| Spring Boot | 自动配置原理、`@ConfigurationProperties`、starter、`application.yml` profile |
| Spring MVC | 请求映射、参数绑定、统一响应体、全局异常处理 `@RestControllerAdvice`、拦截器/过滤器 |
| MyBatis / JPA | SQL 映射、动态 SQL、事务传播、一级/二级缓存、N+1 问题 |
| MySQL | 索引原理（B+ 树）、执行计划 `EXPLAIN`、事务隔离级别与 MVCC、锁、慢查询优化、分页 |
| Redis | 数据结构、过期策略与淘汰、持久化 RDB/AOF、缓存穿透/击穿/雪崩、分布式锁、Lua |
| WebSocket | STOMP 或原生 WS，房间广播、在线状态 |
| 安全 | JWT / Session、密码哈希（BCrypt）、越权与参数校验 `@Valid` |
| 测试 | `@SpringBootTest` 集成测试、Testcontainers（可选）、Mock |

**项目产出（V3：Web 服务）**

1. 用户注册/登录（JWT），玩家表、房间表、对局表、投票记录表（4～5 张表，含索引设计）
2. REST 接口：创建房间、加入、准备、开始、发言、投票、结算
3. WebSocket 推送：房间内实时广播"谁发言了/谁被淘汰了"
4. Redis：房间在线状态（Hash）、排行榜（ZSet）、接口限流（Lua + 固定窗口）
5. 全局异常处理 + 统一响应 + 参数校验 + 日志 traceId
6. 一个简易前端（纯 HTML + JS 即可，不需要学框架），能真的在浏览器里跟朋友玩一局
7. 数据库设计文档 + 接口文档（OpenAPI/Swagger）

**Gate**

- [ ] `EXPLAIN` 能看出并修复一次全表扫描
- [ ] 能用 Redis 正确实现"同一用户 1 分钟只能投票 10 次"的限流
- [ ] 能解释 Spring 三级缓存如何解决循环依赖
- [ ] 接口压测（JMeter/wrk）达到 1000 QPS，写清瓶颈在哪
- [ ] 线上可演示：两个人用两台设备玩一局

**面试可讲点**：*"我做了个 Web 版推理游戏平台，用户/房间/对局三张主表，投票记录用联合索引优化到 2ms；房间状态放 Redis Hash 做水平扩展，WebSocket 广播用发布订阅。"*

### P3（第 13～16 周）：算法与基础冲刺

这一阶段项目暂停，纯啃硬骨头。

**算法（重点）**

- 顺序：数组/双指针 → 链表 → 哈希 → 栈队列 → 二叉树 → 回溯 → 贪心 → 动态规划 → 图 → 堆/并查集
- 题量目标：`Hot 100` 刷完 + 专题补到 250 题
- 要求：**每题限时 20 分钟手写**，写完必须默写一遍，隔 3 天复习
- 产出：一个自己的题解仓库（按专题分目录，每题写"思路 + 复杂度 + 易错点"）

**计算机基础**

- 操作系统：进程/线程/协程、调度、虚拟内存/页表/缺页、文件系统、IO 模型（阻塞/非阻塞/多路复用）
- 网络：HTTP/1.1 vs 2 vs 3、HTTPS 握手、DNS、CDN、TCP 拥塞控制
- 数据库：B+ 树、MVCC、事务隔离、日志（redo/undo/binlog）

**Gate**

- [ ] 随机抽 20 道 mid 难度，60 分钟内 AC ≥ 14 道
- [ ] 能手写：快排、归并、堆排、二分变体、二叉树遍历（递归+非递归）、拓扑排序
- [ ] 能画出"从输入 URL 到页面渲染"的完整链路并解释每一层
- [ ] 能解释 HashMap / MVCC / 线程池 三个源码级问题

### P4（第 17～24 周）：LLM 应用与 Agent 基础

**从这里开始，你的项目开始"有 AI"。**

**学什么**

| 主题 | 内容 |
|---|---|
| LLM 原理（够用即可） | Tokenization、注意力机制的直觉、上下文窗口、温度/top_p、幻觉成因、Function Calling |
| Prompt 工程 | 角色设定、结构化输出（JSON Schema）、Few-shot、CoT、防注入 |
| Context Engineering | 上下文的**组装**：系统提示、人设、规则、历史、检索结果、工具返回值如何排版；token 预算与裁剪策略；信息密度与顺序（Lost in the Middle） |
| Agent 循环 | `观察 → 思考 → 行动 → 观察`，ReAct 模式，工具注册与调用、失败重试、最大步数保护 |
| 工程化 | 流式输出（SSE）、超时与重试、并发控制、成本核算（token 计费）、降级策略 |
| Java 侧生态 | LangChain4j 或 Spring AI（二选一，本项目用 Java 保持技术栈一致） |

**项目产出（V4a：AI 玩家上线）**

1. 定义 `AgentPlayer extends Player`，由 LLM 驱动，与人类玩家同房对局
2. 三个核心 prompt：`发言 prompt`（根据人设+历史+规则生成发言）、`投票 prompt`（输出结构化 JSON：目标 ID + 理由）、`复盘 prompt`
3. 工具集（Function Calling）：`查询存活玩家`、`查询历史投票`、`查询规则`、`查询自己身份`
4. Context 拼装器：`ContextBuilder`，显式管理 token 预算（例如 8k 窗口分配：规则 1k / 人设 0.5k / 历史 4k / 检索 1.5k / 输出预留 1k）
5. 流式输出到 WebSocket，前端能看到 AI "打字"
6. 成本面板：每局消耗 token 数、金额、平均延迟

**Gate**

- [ ] 一局里 3 个人类 + 3 个 AI 能完整跑完，AI 不"出戏"（不会暴露自己是 AI）
- [ ] 投票输出 100% 是合法 JSON，解析失败有兜底重试
- [ ] 能讲清：为什么 Context Engineering 比"把 prompt 写长"更重要
- [ ] 能画出 Agent 的一次完整调用链路图（含工具调用与重试）

**面试可讲点**：*"我设计了一个 ContextBuilder，把上下文分成规则、人设、近期对话、检索记忆四段，按 token 预算动态裁剪；工具调用失败会降级成规则引擎，保证游戏不卡死。"*

### P5（第 25～34 周）：Memory、RAG 与自进化（这是最能拉开差距的一段）

**学什么**

| 主题 | 内容 |
|---|---|
| Embedding | 向量语义、相似度（cosine/dot）、常见 embedding 模型、维度与成本 |
| Vector DB | pgvector（推荐，复用已有 MySQL/PG 经验）、Qdrant、Milvus 的取舍；HNSW/IVF 索引原理与调参 |
| RAG | 文档切分策略（chunk size/overlap）、元数据过滤、混合检索（BM25 + 向量）、Rerank、引用溯源、评估指标（Recall@K / 忠实度） |
| Memory 架构 | 短期（滑动窗口）、工作记忆（本轮对局状态）、长期（摘要 + 向量库）、情节记忆（过往对局）、语义记忆（玩家画像） |
| 记忆写入策略 | 什么值得记（重要性打分）、去重、冲突消解、遗忘/衰减、隐私脱敏 |
| 自进化 | Reflection（赛后复盘生成"经验条目"）、经验入库、下次对局检索注入、A/B 验证是否真的变强 |
| 评测 | 规则断言 + LLM-as-Judge、胜率曲线、回归测试集、消融实验 |

**项目产出（V4b：Agent 有记忆、会变强）**

1. **向量记忆库**：每局结束，把"关键事件"（谁撒谎被识破、什么发言引发了怀疑）embedding 后入 pgvector
2. **玩家画像**：长期记忆中对每个对手形成"风格标签"（激进/保守/爱带节奏），下次对局作为上下文注入
3. **Reflection 循环**：AI 输掉后自动生成 1～3 条"下次应该……"的经验，写入经验库
4. **经验检索**：新对局开始时按当前局势检索 top-k 经验注入 prompt
5. **评测闭环**：写一个 `eval` 模块，固定 100 个种子对局，统计 AI 胜率从 X% → Y%，出对比报告
6. **消融实验**：有记忆 vs 无记忆、有 Reflection vs 无 Reflection，各跑 100 局，出图表

**Gate**

- [ ] AI 胜率因为记忆/反思有**统计显著**的提升（并能在报告里证明不是随机波动）
- [ ] 能讲清 HNSW 的参数含义，以及"为什么召回率高了反而可能更慢"
- [ ] 能讲清"记忆污染"（写入错误经验导致越学越差）的成因和你的防护手段
- [ ] 有 1 篇博客：《我给 AI 玩家做了长期记忆和自进化，胜率提升了 X%》

**面试可讲点**：*"我做了个自进化 Agent：赛后反思生成经验，向量化入库，新对局按局势检索注入。我设计了 100 局固定种子的评测集，做了消融实验，胜率从 41% 提升到 53%，同时发现记忆污染问题，加了重要性阈值和冲突检测。"*
> 这段话的含金量，远超背一百个框架 API。

## 六、AI Agent 专项：把 JD 的四个关键词落到代码里

这一节是本路线和"普通 Java 学习路线"的区别所在。

| 关键词 | 空谈版本（面试会被问穿） | 你要做到的版本 |
|---|---|---|
| **Context Engineering** | "我会写 prompt" | 有一个 `ContextBuilder` 类，显式管理分段、token 预算、优先级裁剪；能解释"为什么把最重要的信息放在开头和结尾"；能展示一次上下文从 8000 token 压到 3000 token 的设计 |
| **Memory** | "我用向量库存对话" | 区分短期/情节/语义三层；有写入策略（重要性打分、去重、冲突）；有读取策略（按局势检索 top-k）；能讲清"记忆污染"和遗忘机制 |
| **自进化** | "我让它自己优化 prompt" | 有 Reflection 产出结构化经验 → 入库 → 检索注入 → **评测集验证**的完整闭环；能拿出胜率曲线和消融实验 |
| **Agent 工程** | "我调过 LangChain" | 能讲清 ReAct 循环、工具注册、失败重试、最大步数、成本控制、超时降级；能画时序图 |

**额外建议**：主项目保持 Java（体现"语言深度"），另外用 Python + LangGraph 做一个 200 行的小 demo（体现"跟进最新技术"）。双栈叙事在面试里很吃香：*"主力是 Java，但 Agent 编排生态在 Python 更成熟，所以我按场景选型。"*

## 八、避坑清单（新手最常犯）

1. ❌ **同时学 Java + Go + Rust + Python** → 一年后四个都会一点，一个都不深。**先 Java 到底，Rust 最后再说。**
2. ❌ **被"AI"吸引，跳过算法和系统** → 简历过不了初筛。JD 权重摆在那。
3. ❌ **只做 CRUD，不碰难点** → 面试官问"你这个项目的技术难点是什么"，答"增删改查"就结束了。
4. ❌ **收藏等于学会** → 视频看了 100 小时，代码写了 0 行。**每看 30 分钟必须写 30 分钟。**
5. ❌ **不写测试** → 重构时不敢动代码，工程能力永远上不去。
6. ❌ **不用 git** → 没有提交历史 = 没有证据证明这些代码是你写的。
7. ❌ **过度设计** → 一上来就微服务、DDD、K8s。**单体跑通再拆。**
8. ❌ **不记录** → 三个月后忘了自己做过什么，简历写不出来。
9. ❌ **只用 AI 写代码而不读** → 会丧失调试能力。**AI 生成的每一行你都要能解释。**
10. ❌ **追求"完美路线"** → 路线是地图不是枷锁，卡住就跳过，回头再补。

## 九、用 AI 的正确姿势（对应 JD 的"AI Native 工作方式"）

1. **让 AI 做"评审"，不做"代写"**：自己写完一段，让 AI 挑毛病（就像这次的代码评审），你负责判断哪些该改。
2. **让 AI 解释，不让 AI 跳过**：看不懂的源码，让 AI 逐行讲，然后你合上电脑用自己的话复述一遍。
3. **写规格再动手**：每个功能先写 10 行"输入/输出/边界/异常"，再让 AI 帮你评估设计，最后才写代码。
4. **用 AI 造测试**：边界值、异常路径，AI 想得比你全；但断言要自己写。
5. **建立"可验证"的习惯**：AI 说什么都要跑一遍、查一遍源码，**幻觉是最大的时间黑洞**。
